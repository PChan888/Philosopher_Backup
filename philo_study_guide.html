Glossary — plain words first

Every new word, defined once

You already know C basics from Rank 0–1: functions, pointers, structs, processes. This project adds exactly one big new idea — threads — and a family of words that come with it. Here they all are, A→Z, each with a one-line meaning and an everyday analogy. Skim it now, come back whenever.

📖 Open the glossary (23 terms, A → Z)
blocked
A thread that is paused on a locked mutex, doing nothing until the lock opens. Analogy: standing outside a locked bathroom — you can't do anything else, you just wait for the key.
circular wait
A waits for B, B waits for C, C waits for A — nobody can ever move. The pattern behind every deadlock at this table. Analogy: four polite people at an intersection, each waving the next one through, forever.
concurrency
Several tasks making progress during the same time span, sharing the same resources. Analogy: five cooks in one kitchen sharing a single stove and fridge.
data race
Two threads touch the same memory at the same moment and at least one writes. C promises nothing about the result. Analogy: two people writing the same word on one whiteboard at once — you get scribble.
deadlock
Two or more threads each hold something the other needs, so all of them wait forever. No crash, no error — the program just freezes. Analogy: two diners, two chopsticks, each holding one chopstick and refusing to let go.
fork
In this project: a shared utensil between two neighbouring philosophers, modelled in code as one mutex. Not the fork() system call that clones a process — same word, totally unrelated.
join
pthread_join: wait for a thread to finish before moving on, and clean up after it. Analogy: a parent waiting at the door until the kid is actually home — only then locking up.
lock / unlock
Taking a mutex / releasing it. Lock blocks you until the mutex is free, then it's yours. Analogy: taking the bathroom key off the hook / hanging it back for the next person.
main thread
The one thread every program starts with — it's what runs main(). In our build, after spawning the philosophers, the main thread becomes the monitor instead of sitting idle.
monitor
A watcher loop that repeatedly scans everyone's state and enforces the global rules (death, meal quota) that no single worker can see alone. Analogy: a lifeguard scanning the whole pool every few seconds.
mutex
“MUTual EXclusion” lock — only one thread can hold it at a time; everyone else waits at lock(). Analogy: a bathroom key — whoever holds it goes, everyone else waits.
mutual exclusion
The rule a mutex enforces: only one thread may use a shared resource at a time. Analogy: one key, one bathroom, one person.
polling
Checking a condition over and over in a loop instead of being notified. Our monitor polls every philosopher twice per millisecond. Analogy: refreshing a package-tracking page every few seconds.
race condition
A timing bug: the outcome changes depending on which thread happens to run first. It may “work” a hundred times, then fail once. Analogy: two roommates both buying milk because each checked the fridge before the other got back.
routine
The function a thread runs, top to bottom; when it returns, the thread ends. Ours is literally named routine(). Analogy: the worker's to-do list — finish the list, go home.
spawn
To create and start a new thread (pthread_create). Analogy: hiring another worker into the same office, effective immediately.
stagger
Deliberately offsetting start times so everyone doesn't lunge for the forks at the same instant. Analogy: boarding a plane by rows instead of all at once.
starvation
No crash, no deadlock — but one thread keeps losing the fight for a resource and never gets a turn, until it's too late. Analogy: always being cut in front of at a buffet: the line moves, you never eat.
stress test
Running the same configuration many times (or for a long time) to force out rare timing bugs that a single run hides. This is how we found our starvation bug.
thread
A second worker inside your program. A process is a separate office with private memory; a thread is another worker in the same office — same memory, same variables, truly running at the same time. Analogy: coworkers sharing one desk and one whiteboard.
thread-safe
Code many threads can run at the same time without corrupting anything — usually because a mutex guards every shared read and write.
ThreadSanitizer
A compiler tool (-fsanitize=thread, “tsan”) that watches every memory access while the program runs and reports data races. Analogy: a referee with instant replay — nothing sneaky gets past it.
undefined behaviour
C's way of saying “no promises”: the program may work, crash, or silently corrupt data — and “it seems to work” proves nothing. Data races cause it.
Part 1 — Philosophy & Logic

The problem, and how our solution thinks

The setup: N philosophers sit at a round table. Between each pair of neighbours lies exactly one fork (just a table utensil — no relation to the fork() call you know from processes). To eat, a philosopher needs both the fork on their left and the fork on their right. After eating they sleep, then think, then get hungry again. If a philosopher goes too long without starting a meal, they die — and the simulation ends.

Dijkstra invented this puzzle in 1965. It looks silly on purpose: the spaghetti hides four serious problems that appear in every concurrent program — a program where several things happen at the same time.

Two words before anything else

🧵 THREAD — the one truly new thing in this project

A thread is a second worker inside your program. You already know processes: a process is a separate office with its own private memory. A thread is another worker in the same office — same memory, same variables, and it truly runs at the same time as the others. Each philosopher will be one thread, all running the same function. The catch: everyone shares one whiteboard, and that sharing causes all four dangers below.

🔑 MUTEX — the tool that tames threads

A mutex (“MUTual EXclusion”) is a lock only one thread can hold at a time — like a bathroom key: whoever holds it goes; everyone else waits at the door. lock() takes the key (and makes you wait — blocked — if someone else has it); unlock() hangs it back. In this project, every fork on the table is one mutex.

The four dangers

⚡ RACE CONDITION

Two threads touch the same memory at the same time and at least one writes. The result is garbage, and it changes run to run depending on who got there first — that unsynchronized access is called a data race. In our code: the monitor (our watcher loop — meet it below) reads last_meal while the philosopher writes it — so both accesses go through meal_lock, a mutex that guards meal data.

🔒 DEADLOCK

Deadlock: everyone grabs their left fork, then waits forever for a right fork that will never come. Nobody can move — no crash, no message, the program just freezes. That circle of waiting is called circular wait — the thing our fork-ordering trick breaks.

🥄 STARVATION

Starvation: no crash, no deadlock — but one unlucky philosopher keeps losing the race for forks, like someone who keeps getting cut in front of at a buffet, and dies slowly. This actually happened to us in testing (see Step 8). It's the sneakiest failure mode.

🚪 MUTUAL EXCLUSION

Mutual exclusion: only one thread may hold a resource at a time. A fork is a pthread_mutex_t: lock it to pick it up, unlock it to put it down. Whoever arrives second simply waits.

The logic our solution uses

🧵 ONE THREAD PER PHILOSOPHER — MONITOR IN MAIN

We spawn (create and start) N threads, each running routine() — the routine is simply the function a thread runs, its to-do list. We do not spawn an extra monitor thread — after creating the philosophers, the main thread itself (the one that runs main()) becomes the monitor by calling monitor(data). One fewer thread to manage, same power.

🍴 ONE MUTEX PER FORK

An array data->forks of N mutexes. Philosopher i owns left_fork = &forks[i] and right_fork = &forks[(i + 1) % nb] — the wrap-around closes the circle.

🔄 DEADLOCK AVOIDANCE: FORK ORDER BY PARITY

In take_forks(): odd IDs lock left first, even IDs lock right first. Two neighbours can never each hold one fork while waiting on the other — the circular wait is broken.

🛡 THREE SHARED LOCKS

print_lock keeps output lines whole. meal_lock guards last_meal + meals_eaten. stop_lock guards the stopped flag. Every shared read/write goes through its lock — that's what makes the code thread-safe. Zero data races (verified with ThreadSanitizer, a compiler tool that watches memory while the program runs).

🧠 FAIRNESS: smart_think()

After sleeping, a philosopher computes its survival margin — how much spare time it has before it would die: time_to_die − (now − last_meal) − time_to_eat. If the margin is comfortable, it waits margin / 2 before grabbing forks — yielding to hungrier neighbours. A starving philosopher waits 0 and grabs immediately.

⏱ PRECISE, INTERRUPTIBLE SLEEP

ft_usleep() never sleeps the full duration at once — it naps in 200µs slices and re-checks has_stopped() each slice, so threads exit almost instantly when the dinner ends.

💀 DEATH DETECTION — WITHIN 10ms

The monitor polls (checks over and over) every 500µs across all philosophers: under meal_lock it computes now − last_meal; if that exceeds time_to_die, it calls set_stop() and prints died — bypassing print_status(), because that helper refuses to print once the simulation has stopped. The death message must be the one exception.

🍝 EDGE CASE: THE LONE PHILOSOPHER

With nb_philos == 1 there is only ONE fork (left and right point at the same mutex — locking both means locking a key you already hold, so you'd wait on yourself forever: a self-deadlock). lone_philo() takes the single fork, announces it, waits time_to_die + 10ms, and lets the monitor declare the death. He can never eat. That's the correct behaviour.

One sentence to remember the whole design N greedy threads + per-fork locks + asymmetric grab order to kill deadlock + an adaptive thinking pause to kill starvation + a polling main thread as judge.

Part 3 — Step-by-Step Build Order

Build it in the order we built it

This is the actual sequence from our session. The rule behind it: data first, callers before callees you can stub, testing last but brutal. Tick each box as you finish — progress is saved in your browser.

1
philo.h — structs & every prototype
Why first: every other file includes this. Once t_philo and t_data exist, you can write any function in any order — the types are the contract. Deciding “what data lives where” IS the design phase.
2
main.c — validate args, spawn & join threads
Why second: everything downstream trusts its input, so validation must exist before logic. Writing start_simulation() now (calling functions that don't exist yet) forces you to design the whole program's skeleton — the header's prototypes make that legal.
3
init.c — mutexes, philosophers, cleanup
Why third: threads can't run before their world exists. Build free_data() in the same sitting as init_data() — every resource you create, you immediately know how to destroy. Handle the malloc/init failure paths NOW, not later.
4
routine.c — the philosopher life cycle
Why fourth: this is the heart. Get ONE philosopher's loop right (take forks → eat → sleep → think), then parity ordering makes N of them coexist. Includes lone_philo() — write the edge case while the fork logic is fresh in your head.
5
monitor.c — stop flag & death watch
Why fifth: the routine loops on has_stopped(), so the stop machinery is what turns “N infinite loops” into a program that ends. Death check + meal-count check + the thread-safe flag all live here.
6
utils.c — time, sleep, print, atol
Why now: you've been calling get_time_ms() / ft_usleep() / print_status() since step 4 — now give them real bodies. Written last among the .c files because their exact behaviour (slice size, stop checks) is dictated by how the routine and monitor use them.
7
Makefile — -Wall -Wextra -Werror -pthread
Why here: trivial but graded. all clean fclean re, no relink, and don't forget -pthread — without it the pthread functions may link but misbehave.
8
Test & tune — where the real bugs live
Why brutal testing matters: our first version passed single runs of every config — then five 8-second stress runs of ./philo 5 800 200 200 produced intermittent deaths. Odd counts + timing drift = slow starvation. The fix was smart_think(). Run each config 5+ times; race bugs don't show up on demand. Check with ThreadSanitizer (-fsanitize=thread) and norminette.

Part 5 — Reference Notes & Citations

Man pages, articles, concepts

Man pages you'll live in

  • man 3 pthread_create pthread_create(3) — spawn a thread running void *fn(void *). Ours: pthread_create(&philo.thread, NULL, &routine, &philo).
  • man 3 pthread_join pthread_join(3) — wait for a thread to finish (join it). Skipping it = threads killed mid-work + leaked resources.
  • man 3 pthread_mutex_lock pthread_mutex_lock(3p) — blocks (pauses your thread) until the lock is yours. Locking a mutex you already hold (lone-philosopher trap) = undefined/deadlock.
  • man 3 pthread_mutex_init pthread_mutex_init(3p) / destroy — init before use, destroy exactly once, never destroy a locked mutex.
  • man 2 gettimeofday gettimeofday(2) — µs-resolution wall clock; our get_time_ms() converts to ms: sec * 1000 + usec / 1000.
  • man 3 usleep usleep(3) — sleeps at least that long (OS may oversleep). Why ft_usleep slices 200µs naps instead of one big sleep.

The problem itself

  • original paper E.W. Dijkstra, “Hierarchical Ordering of Sequential Processes” (EWD-310) — where the dining philosophers were born (as “dining quintuple”), 1965/71.
  • overview Wikipedia — Dining philosophers problem — survey of solutions; ours is the “resource ordering” family (asymmetric acquisition: neighbours grab forks in different orders).
  • deadlock theory Coffman conditions — the 4 conditions that must ALL hold for deadlock. Break any one, deadlock is impossible. Parity fork order breaks circular wait.
  • tooling ThreadSanitizer docs — -fsanitize=thread; how we proved zero data races. Slows the program ~5-15× — use short runs.

Concepts referenced above — 10-second recap

thread

An execution lane sharing the process's memory — a coworker at the same desk. Cheap, parallel, dangerous together.

mutex

A lock — the bathroom key. One owner at a time; everyone else blocks on lock() until unlock().

data race

Unsynchronized access to shared memory, ≥1 writer — two hands scribbling one whiteboard. Undefined behaviour — even if it “seems to work”.

circular wait

A → waits for B → waits for C → waits for A. The Coffman condition our parity trick removes.

starvation

A thread that never wins the resource race — forever cut in line at the buffet. Fixed by fairness (smart_think), not by locks alone.

monitor pattern

One watcher — a lifeguard — polling shared state to enforce global rules (death, meal quota) the workers can't see alone.

Last thing before your defense Be ready to answer: why can't a philosopher check their own death? (Because a philosopher blocked on pthread_mutex_lock can't run any code — only an outside observer can catch a starving, blocked thread in time.)
