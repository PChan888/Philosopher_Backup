Part 0 — The Big Picture

What is Philosophers and what will you learn?

In one sentence: you simulate multiple philosophers sitting at a round table, each running in their own thread, sharing forks (protected by mutexes) to eat spaghetti — without anyone starving or the program crashing.

🧠 Why does this project exist?

Until now, your programs ran one instruction at a time, from top to bottom, like a single conveyor belt. Philosophers is the first time you have multiple conveyor belts running simultaneously — each philosopher is doing their own thing at the same time. This is called concurrent programming, and it's how modern software works: your browser tabs, background downloads, and notifications all run "at the same time." Learning to handle this safely is one of the most important skills in software engineering.

How this connects to what you already know

libft / push_swap struct
Centralized state struct → t_philo struct holds all philosopher state
so_long / fract'ol event loop
Infinite loop checking state → philosopher routine loops eat/sleep/think
minitalk signal handling
Async events between processes → threads running simultaneously, needing sync
push_swap no globals rule
Struct holds everything → same rule here, even more critical with threads

The three big concepts you'll learn

1. Threads — Imagine your program is a restaurant. Until now, you had one chef doing everything: take order, cook, serve, clean. A thread is like hiring multiple chefs. They all share the same kitchen (memory), but each works on their own task simultaneously. Each philosopher is one chef (one thread).

2. Mutexes — Now imagine there's only one knife in the kitchen. If two chefs grab it at the same time, disaster. A mutex is like a lock on the knife drawer: one chef locks it, uses the knife, then unlocks it. While locked, any other chef who tries the drawer has to wait. In your project, forks are protected by mutexes.

3. Data races — If two chefs both read the order ticket at the same time and both start making the same dish, that's a data race: two threads reading/writing the same memory without coordination. Your program must have zero data races. The subject is very strict about this.

Part 1 — Threads

What is a thread?

Remember how a process works? When you run ./philo, your OS creates a process — it gets its own chunk of memory, its own program counter (which line of code it's on), its own stack. Everything is isolated.

A thread is like a lightweight process that lives inside a process. Multiple threads share the same memory space (heap, global data) but each thread gets its own:

Thread vs Process — the apartment analogy A process is an entire apartment. A thread is a roommate. All roommates share the kitchen, living room, and bathroom (shared memory), but each has their own bedroom (stack) and to-do list (program counter). They can work on different things simultaneously, but if two try to use the bathroom at the same time... problems.

The 4 thread functions you'll use

pthread_create — spawn a new thread
int pthread_create(
    pthread_t *thread,           // pointer to store the thread ID
    const pthread_attr_t *attr,  // attributes (always NULL for us)
    void *(*start_routine)(void *), // the function the thread will run
    void *arg                    // argument passed to that function
);

// Example: create a thread that runs philosopher_routine
pthread_t    tid;
t_philo      *philo;

pthread_create(&tid, NULL, philosopher_routine, (void *)philo);
// Now philosopher_routine is running IN PARALLEL with main!

The key insight: after pthread_create returns, two things are running at the same time: your main function continues to the next line, AND the new thread starts executing philosopher_routine. This is fundamentally different from a regular function call.

pthread_join — wait for a thread to finish
int pthread_join(
    pthread_t thread,   // which thread to wait for
    void **retval       // store return value (NULL for us)
);

// Example: main waits until thread finishes
pthread_join(tid, NULL);
// Execution only reaches here AFTER the thread is done

Think of pthread_join like waitpid for processes. If your main function exits without joining threads, the threads get killed mid-work. Always join your threads.

pthread_detach — let thread clean itself up
pthread_detach(tid);
// Thread resources auto-freed when it finishes
// You can't join a detached thread
// Most philo solutions use join, not detach

The thread function signature

The function you pass to pthread_create MUST have this exact signature:

void    *philosopher_routine(void *arg)
{
    t_philo    *philo;

    philo = (t_philo *)arg;   // cast void* back to your struct
    // ... do philosopher stuff ...
    return (NULL);
}
Why void*? The pthread library is generic — it doesn't know about your custom structs. So it uses void * (a pointer to "anything"). You cast your struct pointer to void * when passing it in, and cast it back inside the function. You did something similar with MiniLibX hooks in so_long and fract'ol — the void *param that gets passed to your hook functions is the same concept!

Concrete example: your first threaded program

// Try this! Compile with: cc -pthread threads_demo.c
#include <pthread.h>
#include <stdio.h>
#include <unistd.h>

void    *say_hello(void *arg)
{
    int    id = *(int *)arg;
    printf("Thread %d: Hello!\n", id);
    usleep(500000);  // sleep 0.5 sec
    printf("Thread %d: Goodbye!\n", id);
    return (NULL);
}

int    main(void)
{
    pthread_t    threads[3];
    int          ids[3] = {1, 2, 3};

    for (int i = 0; i < 3; i++)
        pthread_create(&threads[i], NULL, say_hello, &ids[i]);
    for (int i = 0; i < 3; i++)
        pthread_join(threads[i], NULL);
    printf("All threads done!\n");
    return (0);
}
// Output order is UNPREDICTABLE! That's the nature of threads.
Part 2 — Mutexes

What is a mutex?

"Mutex" stands for MUTual EXclusion. It's a lock that ensures only one thread can access a piece of shared data at a time. Think of it literally as a lock on a bathroom door.

🚪 The bathroom analogy — traced step by step

Without mutex: Thread A checks if bathroom is free (yes). Thread B checks if bathroom is free (yes — it hasn't changed yet!). Both walk in. Chaos. This is a data race.

With mutex: Thread A calls pthread_mutex_lock → door locks. Thread B calls pthread_mutex_lock → sees it's locked → waits (blocks, does nothing). Thread A finishes, calls pthread_mutex_unlock → door unlocks. Thread B's lock call finally returns → Thread B enters.

The 4 mutex functions

// 1. Initialize: create the lock (must do before using)
pthread_mutex_t    fork_mutex;
pthread_mutex_init(&fork_mutex, NULL);

// 2. Lock: "I'm using this now, everyone else wait"
pthread_mutex_lock(&fork_mutex);
// ... safe to use the shared resource ...

// 3. Unlock: "I'm done, next person can use it"
pthread_mutex_unlock(&fork_mutex);

// 4. Destroy: clean up when done (at program exit)
pthread_mutex_destroy(&fork_mutex);

Why you need mutexes in this project

In Philosophers, the shared resources are:

Forks — Each fork sits between two philosophers. If philosopher 1 and philosopher 2 both try to grab the same fork at the same time without a mutex, you get a data race. Each fork gets its own mutex.

Print output — If two philosophers try to printf at the same time, their output can get mixed up: "0 1 has ta2 is eken a forksleeping". You need a "print mutex" so only one philosopher prints at a time.

Death flag / last_meal time — A monitor thread reads last_meal_time to check if a philosopher has starved. Simultaneously, the philosopher thread writes to it when they eat. Without a mutex protecting this, you get a data race.

Data race example — with actual numbers

SCENARIO: Two threads reading/writing "last_meal_time" = 1000

WITHOUT MUTEX (data race!):
Time    Thread A (philosopher)    Memory         Thread B (monitor)
────    ────────────────────────  ──────────     ──────────────────
  1     wants to write 2000       [1000]         reads → gets 1000
  2     writes high byte          [20|00]        reads → gets GARBAGE!
  3     writes low byte           [2000]

WITH MUTEX (safe):
Time    Thread A (philosopher)    Lock    Memory    Thread B (monitor)
────    ────────────────────────  ────    ──────    ──────────────────
  1     lock() → got it           🔒     [1000]    lock() → WAITS...
  2     writes 2000               🔒     [2000]    ...still waiting...
  3     unlock()                  🔓     [2000]    lock() → got it!
  4                               🔒     [2000]    reads → gets 2000 ✓
  5                               🔓     [2000]    unlock()
The #1 rule of mutexes Every pthread_mutex_lock must have a matching pthread_mutex_unlock. If you lock and forget to unlock, other threads wait forever — this is called a deadlock. If you unlock without locking first, that's undefined behavior.
Part 3 — The Dining Philosophers Problem

Understanding the classic problem

This is one of the most famous problems in computer science, invented by Edsger Dijkstra in 1965. Here's the setup, matched to what the subject requires:

5 philosophers at a round table (example with 5):

           [P1]
        🍴      🍴
      [P5]       [P2]
       🍴  🍝    🍴
      [P4]       [P3]
           🍴

    🍴 = fork (mutex)
    🍝 = spaghetti (unlimited)
    [Pn] = philosopher (thread)

    Each philosopher needs BOTH adjacent forks to eat.
    P1 needs fork between P1-P5 AND fork between P1-P2.

The philosopher lifecycle

Each philosopher does exactly three things in a loop, forever:

// The philosopher's eternal routine:
while (nobody_died && !all_ate_enough)
{
    pick_up_forks();     // grab left and right fork (lock 2 mutexes)
    eat();               // eat for time_to_eat ms, update last_meal_time
    put_down_forks();   // release both forks (unlock 2 mutexes)
    sleep_philo();       // sleep for time_to_sleep ms
    think();             // think until forks available
}

The two deadly problems

Problem 1: Deadlock — Imagine all 5 philosophers pick up their LEFT fork at exactly the same time. Now everyone holds one fork and needs the fork to their right — which is held by their neighbor. Nobody can eat. Nobody releases their fork. Everyone waits forever. Everyone dies.

DEADLOCK scenario:

    P1 grabs fork_1 (left) → wants fork_2 (right) → held by P2!
    P2 grabs fork_2 (left) → wants fork_3 (right) → held by P3!
    P3 grabs fork_3 (left) → wants fork_4 (right) → held by P4!
    P4 grabs fork_4 (left) → wants fork_5 (right) → held by P5!
    P5 grabs fork_5 (left) → wants fork_1 (right) → held by P1!
    
    🔴 Circular wait → DEADLOCK → everyone starves

Solution: Break the cycle! Make even-numbered philosophers pick up their RIGHT fork first, odd-numbered pick up LEFT first. This breaks the circular dependency because not everyone reaches for the same direction.

if (philo->id % 2 == 0)
{
    pthread_mutex_lock(philo->right_fork);  // even: right first
    pthread_mutex_lock(philo->left_fork);
}
else
{
    pthread_mutex_lock(philo->left_fork);   // odd: left first
    pthread_mutex_lock(philo->right_fork);
}

Problem 2: Starvation — Even without deadlock, a philosopher might never get to eat because their neighbors keep eating first. The timing parameters (time_to_die, time_to_eat, time_to_sleep) determine if this happens. If time_to_die is less than time_to_eat + time_to_sleep, someone will starve — and your program must detect the death within 10ms.

The time_to_die rule — the most misunderstood part

Critical: what "time_to_die" actually means A philosopher dies if they haven't started eating within time_to_die milliseconds since their last meal began (or since simulation start if they haven't eaten yet). It's measured from the START of the last eat, not from the end. 
Example: time_to_die=800, time_to_eat=200, time_to_sleep=200

Philosopher 1 timeline:
  t=0     simulation starts, last_meal_time = 0
  t=0     picks forks, starts eating (last_meal_time = 0)
  t=200   finishes eating
  t=200   starts sleeping
  t=400   wakes up, starts thinking
  t=400   picks forks, starts eating (last_meal_time = 400)
  ...
  If at any point: current_time - last_meal_time >= 800 → DEAD

The monitor — checking for death

You need a way to constantly check if any philosopher has starved. The common approach: a monitor thread (or the main thread after creating all philosopher threads) that loops and checks each philosopher's last_meal_time.

void    *monitor_routine(void *arg)
{
    t_data    *data = (t_data *)arg;
    int       i;

    while (1)
    {
        i = 0;
        while (i < data->num_philos)
        {
            pthread_mutex_lock(&data->meal_mutex);
            if (get_time() - data->philos[i].last_meal_time
                >= data->time_to_die)
            {
                print_status(&data->philos[i], "died");
                pthread_mutex_lock(&data->stop_mutex);
                data->stop = 1;
                pthread_mutex_unlock(&data->stop_mutex);
                pthread_mutex_unlock(&data->meal_mutex);
                return (NULL);
            }
            pthread_mutex_unlock(&data->meal_mutex);
            i++;
        }
        usleep(1000);  // check every 1ms (don't busy-wait)
    }
}
Part 4 — Data Structures

Designing your structs

Just like in push_swap where your t_stack held everything about a node, and in fract'ol where t_fractol held all state — here you need structs for the shared data and per-philosopher data.

// Shared data — one instance for the whole simulation
typedef struct s_data
{
    int               num_philos;
    long              time_to_die;
    long              time_to_eat;
    long              time_to_sleep;
    int               must_eat_count;   // -1 if not specified
    long              start_time;       // simulation start timestamp
    int               stop;             // flag: someone died or all ate
    pthread_mutex_t   *forks;           // array of fork mutexes
    pthread_mutex_t   print_mutex;      // protect printf
    pthread_mutex_t   stop_mutex;       // protect the stop flag
    pthread_mutex_t   meal_mutex;       // protect last_meal reads/writes
    t_philo           *philos;          // array of philosopher structs
}   t_data;

// Per-philosopher data — one per philosopher
typedef struct s_philo
{
    int               id;               // 1 to num_philos
    int               meals_eaten;
    long              last_meal_time;   // timestamp of last eat START
    pthread_t         thread;           // this philosopher's thread
    pthread_mutex_t   *left_fork;       // pointer to fork mutex
    pthread_mutex_t   *right_fork;      // pointer to fork mutex
    t_data            *data;            // pointer back to shared data
}   t_philo;
Why pointers for forks? The actual mutex objects live in data->forks[] array. Each philosopher just stores pointers to their two neighboring mutexes. This way, philosopher 1's right_fork and philosopher 2's left_fork point to the same mutex — the shared fork between them. This is exactly like how in push_swap, nodes stored pointers rather than copies of data.

Fork assignment — the round table math

// Assign forks to each philosopher
for (i = 0; i < data->num_philos; i++)
{
    data->philos[i].left_fork = &data->forks[i];
    data->philos[i].right_fork = &data->forks[(i + 1) % data->num_philos];
    // The modulo wraps around: last philosopher's right fork = fork[0]
}

// With 5 philosophers:
// P0: left=fork[0], right=fork[1]
// P1: left=fork[1], right=fork[2]
// P2: left=fork[2], right=fork[3]
// P3: left=fork[3], right=fork[4]
// P4: left=fork[4], right=fork[0]  ← wraps around!
Part 5 — Time Management

Getting and using timestamps

Everything in this project is measured in milliseconds. You need two time utilities:

// Get current time in milliseconds
long    get_time(void)
{
    struct timeval    tv;

    gettimeofday(&tv, NULL);
    return ((tv.tv_sec * 1000) + (tv.tv_usec / 1000));
    // tv_sec  = seconds since Jan 1, 1970
    // tv_usec = microseconds (additional)
    // We convert everything to milliseconds
}

// Precise sleep function (usleep alone is not accurate enough)
void    ft_usleep(long ms, t_data *data)
{
    long    start;

    start = get_time();
    while (get_time() - start < ms)
    {
        if (is_simulation_stopped(data))
            break;
        usleep(500);  // sleep 0.5ms then check again
    }
}

// Print with timestamp relative to start
void    print_status(t_philo *philo, char *status)
{
    long    timestamp;

    pthread_mutex_lock(&philo->data->print_mutex);
    if (!is_simulation_stopped(philo->data))
    {
        timestamp = get_time() - philo->data->start_time;
        printf("%ld %d %s\n", timestamp, philo->id, status);
    }
    pthread_mutex_unlock(&philo->data->print_mutex);
}
Why not just usleep? usleep(200000) means "sleep at least 200ms" — but it could sleep 201ms or 205ms due to OS scheduling. Over many cycles, this drift adds up and a philosopher could die because you slept too long. The ft_usleep function uses a busy-wait loop: sleep a tiny bit, check the real time, sleep again if needed. This keeps you within ~1ms accuracy.

The main flow

int    main(int argc, char **argv)
{
    t_data    data;

    // 1. Parse & validate arguments
    if (argc != 5 && argc != 6)
        return (printf("Error: wrong number of arguments\n"), 1);
    if (parse_args(&data, argc, argv))
        return (1);

The philosopher routine — heart of the project

void    *philosopher_routine(void *arg)
{
    t_philo    *philo;

    philo = (t_philo *)arg;
    // Stagger start: even philosophers wait a tiny bit
    // This prevents everyone grabbing forks at once
    if (philo->id % 2 == 0)
        ft_usleep(philo->data->time_to_eat / 2, philo->data);
    while (!is_simulation_stopped(philo->data))
    {
        eat(philo);
        sleep_philo(philo);
        think(philo);
    }
    return (NULL);
}

void    eat(t_philo *philo)
{
    // Lock forks in consistent order to prevent deadlock
    if (philo->id % 2 == 0)
    {
        pthread_mutex_lock(philo->right_fork);
        print_status(philo, "has taken a fork");
        pthread_mutex_lock(philo->left_fork);
        print_status(philo, "has taken a fork");
    }
    else
    {
        pthread_mutex_lock(philo->left_fork);
        print_status(philo, "has taken a fork");
        pthread_mutex_lock(philo->right_fork);
        print_status(philo, "has taken a fork");
    }
    // Update last meal time (protected by meal_mutex)
    pthread_mutex_lock(&philo->data->meal_mutex);
    philo->last_meal_time = get_time();
    philo->meals_eaten++;
    pthread_mutex_unlock(&philo->data->meal_mutex);
    print_status(philo, "is eating");
    ft_usleep(philo->data->time_to_eat, philo->data);
    // Release forks
    pthread_mutex_unlock(philo->left_fork);
    pthread_mutex_unlock(philo->right_fork);
}

void    sleep_philo(t_philo *philo)
{
    print_status(philo, "is sleeping");
    ft_usleep(philo->data->time_to_sleep, philo->data);
}

void    think(t_philo *philo)
{
    print_status(philo, "is thinking");
}

Special case: 1 philosopher

// With only 1 philosopher, there's only 1 fork.
// They pick it up, but can never pick up a second one.
// They must die after time_to_die.
if (data->num_philos == 1)
{
    print_status(&data->philos[0], "has taken a fork");
    ft_usleep(data->time_to_die, data);
    print_status(&data->philos[0], "died");
    return;
}

The stop check — thread-safe flag reading

int    is_simulation_stopped(t_data *data)
{
    int    stopped;

    pthread_mutex_lock(&data->stop_mutex);
    stopped = data->stop;
    pthread_mutex_unlock(&data->stop_mutex);
    return (stopped);
}
// Every time any thread reads "data->stop", it must lock/unlock.
// This prevents data races on the stop flag itself.

Death timing rule When testing ./philo 1 800 200 200, the death message must appear between 800ms and 810ms. If it says "813 1 died" — you're too slow. Your ft_usleep or monitor check interval is too coarse. Reduce the usleep inside your monitor and ft_usleep to 500 microseconds.

Supportive learning materials

Watch first (visual learners): Search YouTube for "CodeVault pthreads" — this channel has a series of short videos (~5 min each) that cover pthread_create, pthread_join, mutexes, and the dining philosophers specifically. Watch the first 5-6 videos before starting.

Read second (concept depth): The man pthread_create, man pthread_mutex_lock pages are short and clear. Read them once — they'll demystify the function signatures.

Debug with: -fsanitize=thread (compile flag) is your best friend for finding data races. It will tell you exactly which line of code has a race. Valgrind with --tool=helgrind is another option.

Thinking framework: For every variable in your structs, ask: "Can two threads read/write this at the same time?" If yes → protect it with a mutex. This single question will prevent 90% of bugs.
